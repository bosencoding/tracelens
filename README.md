# TraceLens v2 — JPEG signature identification

Upload one JPEG, read what the file itself carries, get a camera/encoder verdict, print a short
report. Indonesian UI.

> **DATA SINTETIS.** Every sample photo, every reference profile and every number in this repo is
> generated by `backend/app/seed.py` with Pillow. No real camera profile, no real forensic result.
> The UI footer and the printed report both say so.

Goal v1 (PRNU: sensor fingerprint, PCE, wavelets, hot pixels, ECDSA seal, server PDF) was
**discarded** at the product owner's request — overkill for a coursework deliverable. v2 identifies
the signature a JPEG actually carries:

| layer | what it reads | how |
|---|---|---|
| EXIF identity | Make, Model, LensModel, Software, DateTimeOriginal, SerialNumber, MakerNote | Pillow `getexif()` + embedded thumbnail scan |
| Quantization tables | the 2 tables (64+64 values) | Pillow `.quantization`, cosine x scale vs 3 references |
| Encoder fingerprint | APP markers, subsampling, restart interval, DHT count, IJG table match | small marker walker (`app/jpeg.py`) |
| Edit trace | thumbnail vs main tables, luma/chroma quality mismatch, Software after capture, MakerNote missing | comparisons in `app/analyze.py` |

No PRNU, no wavelet, no PCE, no SNR, no hot pixels, no clustering, no ECDSA, no server PDF, no auth.

## Stack

Vue 3.5 + TypeScript + Vite 8 + Tailwind 3.4 · FastAPI + Pydantic v2 (Python 3.11, `uv`) + Pillow ·
**SQLite** — one file `backend/data/tracelens.db`, created automatically, stdlib `sqlite3` only,
schema in `backend/sql/schema.sql`. No Postgres, no Supabase, no docker, no RLS, no keys.

## Run it (two terminals)

```sh
# backend :8001
cd backend
uv sync
uv run python -m app.seed     # 3 reference profiles + 7 synthetic JPEGs (idempotent)
uv run uvicorn app.main:app --host 127.0.0.1 --port 8001

# frontend :5173
cd frontend
npm install
npm run dev -- --port 5173
```

Open <http://localhost:5173>. Production build: `cd frontend && npm run build` → `dist/` (196 KB).

## Routes

| route | contents |
|---|---|
| `/` | drop zone (`.jpg/.jpeg`, max 50 MB) + saved-evidence list with verdict and delete |
| `/hasil/:id` | verdict card + 4 tabs: EXIF · Tabel Kuantisasi · Jejak Edit · Ringkasan |
| `/laporan/:id` | print document (`@media print` drops nav/buttons), disclaimer + method limits |
| `/pengaturan` | runtime settings: upload limit (1–500 MB) + read-only info (db path, evidence count, version) |
| anything else | explicit "halaman tidak ditemukan" card, never a blank page |

## API

| method | path | notes |
|---|---|---|
| POST | `/api/evidence` | multipart `file`; 415 for non-JPEG, 413 for >50 MB, 422 for empty/unreadable |
| GET | `/api/evidence` | history, newest first |
| GET | `/api/evidence/{id}` | evidence + signature + top-3 matches |
| GET | `/api/evidence/{id}/signature` | EXIF, qtable pair, fingerprint hex, encoder info, traces, component scores |
| GET | `/api/evidence/{id}/matches` | 3 candidates, similarity descending |
| GET/HEAD | `/api/evidence/{id}/image` | original bytes, `image/jpeg`, correct `Content-Length`, `ETag` = file sha256; 410 if the file vanished |
| GET/HEAD | `/api/evidence/{id}/thumbnail` | ≤480 px JPEG built per request (EXIF orientation honoured), `Cache-Control: private, max-age=3600`, `ETag`, 304 on `If-None-Match`; no derivative file written |
| DELETE | `/api/evidence/{id}` | 204, removes row and stored file |
| GET | `/api/settings` | `{max_upload_mb, db_path, evidence_count, app_version}` |
| PATCH | `/api/settings` | body `{max_upload_mb}` 1–500; 422 with `fields:["max_upload_mb"]`; loopback/CORS-origin only, else 403 |

Errors are uniform `{detail, code}` (`fields` on 422). CORS allows `http://localhost:5173`.

## Evidence preview

`/hasil/:id` shows a fixed-ratio (`aspect-[4/3]`, `object-fit: cover`) thumbnail card with the file
name, dimensions, size in MB and a "Lihat ukuran penuh" link to `/image`; the list on `/` shows a
40 px thumbnail per row. Both images come from the API:

- `/image` serves the stored file **unchanged** — no re-encode, so the sha256 in the DB still matches
  the bytes on disk (verified before and after a thumbnail request).
- `/thumbnail` is generated on demand with Pillow (`draft` → `exif_transpose` → `thumbnail` 480 px)
  and returned from memory; nothing is written to the upload directory.
- Both take the id from the DB, never a path from the caller; unknown id → 404 `not_found`, missing
  file on disk → 410 `file_missing`, unreadable file → 422 `image_unreadable`. No absolute path is
  ever in a response body.

## Runtime settings

`GET /api/settings` and `PATCH /api/settings` back the `/pengaturan` page. The value lives in the
SQLite `settings` table (`key`, `value`, `updated_at`) and is the single source of truth:

- `MAX_UPLOAD_MB` from the environment only **seeds** a database that has no row yet; after that a
  UI change wins and survives a restart (the table is created by the idempotent schema on boot).
- `POST /api/evidence` reads the limit from the table, so the 413 message always quotes the active
  number, and the upload page reads the same value for its client-side check — no constant in the
  bundle.
- Range is 1–500 MB; `0`, `501`, `"abc"` and a missing field all return 422 with
  `fields: ["max_upload_mb"]`.

**Security (no auth in this app).** `PATCH /api/settings` is accepted only from loopback
(`127.0.0.1`, `::1`) or an allowed CORS origin; anything else gets 403 `{detail, code}`. That stops
a random machine on the LAN from changing the limit, but the `Origin` header is spoofable by
non-browser clients, so it is not real authorisation — anyone who can reach the port can still
`GET` the settings, and a hostile local process is out of scope. Add auth before exposing this
service beyond your machine.

## How the numbers are produced (no client literals)

```
similarity(table, ref) = cosine(table, ref) x (1 - |mean(table) - mean(ref)| / max(mean))
      # cosine alone cannot separate qualities: IJG tables are near-parallel (cos ~0.999
      # between q75 and q92), so the magnitude term carries the quality signal
fingerprint_hex        = sha256( json( both tables / their own max, 4 decimals ) )
confidence             = 0.45 x EXIF + 0.35 x best_qtable_similarity + 0.20 x encoder_score
bands                  = >=0.75 kuat, >=0.55 sedang, >=0.45 lemah, else tidak dapat dipastikan
encoder                = APP14 Adobe > Software tag (Adobe/Apple) > exact IJG tables > near-IJG
```

Everything the UI shows comes from `GET /api/evidence/{id}/signature`; the tab test asserts the
rendered fingerprint and qtable cell equal the API payload.

## Real datasets (importer)

Any folder of JPEGs can become reference rows — no code change:

```sh
cd backend
uv run python -m tools.import_reference --dir ~/datasets/SOCRatES --label-prefix soc --dry-run
uv run python -m tools.import_reference --dir ~/datasets/SOCRatES --label-prefix soc
uv run python -m tools.import_reference --list sidecar.csv --update   # path per line
uv run python -m tools.import_reference --dir ~/datasets/x --max-mb 60 # opt-in size cap
```

Groups by EXIF `Make`+`Model`, takes the per-position median of each quantization table,
labels the row `<prefix> <make> <model>`, id `REF-<sha1(make|model)[:8]>`. Idempotent: a
second run reports existing ids as `tetap` and writes nothing unless `--update` is passed.
`--dry-run` writes nothing at all — it will not even create the database file. Seed rows
`REF-A/B/C` are untouched.

**No size cap by default.** A reference import is not an API upload, so `MAX_UPLOAD_MB` (50 MB)
does not apply: real camera files run 40 MB and bigger (DJI 36–39 MB, Hasselblad 44 MB in the
dpreview set) and any upload-sized cap silently drops whole brands. `--max-mb N` sets a cap when you want
one; `--max-mb 0` (default) means unlimited.

**Normalisation.** EXIF strings arrive NUL-padded (`Sigma BF\x00\x00`) or space-padded
(`PENTAX K-3 Mark III   `). Make/model are stripped of NULs and collapsed to single spaces, and
grouping compares casefolded text, so padding or case never splits one camera into two rows; the
label keeps the original spelling. Different model codes stay separate on purpose (DJI `FC8282`
vs `FC8284` are different bodies).

**Never silently a camera.** Files with no Make/Model are labelled `TANPA-EXIF/<folder>`, and
lab-scanner EXIF (`NORITSU`, `FRONTIER`, `QSS`, `EZ Controller`) is labelled `SCAN/<make> <model>`;
both carry a `what_if` that says the row is not a camera sensor, and the run ends with a summary
line plus a warning per kind:

```
file=100 grup=21 berkas_dilewati=0 baru=21 | kamera=18 scan=1 tanpa-exif=2
```

Unreadable or single-table (grayscale) files are skipped, listed with the reason, and counted as
`berkas_dilewati=`, never fatal. Note that two cameras whose JPEG pipeline shares one encoder
setting produce the *same* median table and therefore the same fingerprint — tables identify the
pipeline, not the body; the label is the only thing that distinguishes those rows.

EXIF and quantization tables are read through `app.analyze.identity()` / `qtable_pair()`, the
same functions the upload analyzer uses, so an importer row means what the app means by a table.

Caveat: only **camera-native JPEGs** carry the camera's own tables. RAW (e.g. RAISE `.NEF/.CR2`)
must not be converted first — Pillow/libjpeg would write its own tables and you would fingerprint
the converter, not the camera.
